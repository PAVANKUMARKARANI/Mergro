How the backend and the app get built

The backend is the Express + MongoDB server in Mergro/server, and the app is the Flutter + Riverpod project in Mergro-Mobile-App. Phases and weeks come from the project spreadsheet's 16-week roadmap.

Done built and in the code today UI ready screen built with demo data, API not connected yet Next start now Planned later phase

Already built

  • App, connected to the server: splash, login, forgot password, onboarding for admin, agent and team lead, sign-out
  • App, UI with demo data: app shell with role-based tabs, Home dashboard (4), Leads + search (5, 11), Live calls (6), Hot lead inbox (7), Viewings (8), Nurture (9), Profile (10)
  • App, UI with demo data: Lead profile (13) with qualification (16), score (17), activity (19) and consent (20); call-back, message and do-not-contact actions
  • App, UI with demo data: Live call monitor (12), Call detail (14), Transcript with masked personal data (15), Book viewing with a 5-minute hold (18)
  • App: Light / Dark / System theme choice, skeleton loading on every list
  • Server: /api/auth/*, /api/onboarding/*, /api/team/invites, 5 roles, seed users
  • Server: leads API — ingestion webhook with per-brokerage key, dedupe, consent and calling-hours eligibility, list / profile / timeline, consent withdrawal, suppression

Build next

  • App: handoff module (21–26) as UI with demo data, or connect screens to the lead / call API as it lands
  • App: connect Leads, the lead profile and dashboard counts to /api/leads
  • Server: call job queue and telephony adapter (Voice AI phase)

Notes

  • The project documents suggested FastAPI and PostgreSQL. Your server is Express 5 and MongoDB, so these graphs follow the server you have.
  • Statuses come from the code in Mergro/server and Mergro-Mobile-App. Discovery and architecture items show as planned because nothing in the code records them.
  • UI ready screens load demo data after a short delay and mark each missing call with TODO(backend) in the code; the endpoint list lives in skill.md's TODO(backend) table. They become Done when their API is connected.
  • The voice runtime (speech-to-text, LLM, text-to-speech) is the riskiest piece. Building a throwaway test call early in phase 4 shows whether response times are fast enough before the rest depends on it.
